# Badminton Rally Analyzer — frontend repo (beta prototype)

Read this first. It describes what this app does, how it talks to the backend, the
decisions already made, and the milestones in order.

- Backend repo: `../badminton-backend` (GitHub: LukeySan/badminton-be). Its README
  section **"Using it from the frontend"** and its `CLAUDE.md` are the source of truth
  for the API's behavior.
- Research history and numbers: `../CLAUDE.md` and `../badminton-test/`.
- Visual design: **`DESIGN.md`** — all UI work must follow it (see Conventions).

## What the app does

Players record a match on a phone on a tripod and upload it. The backend finds every
**rally** (start/end time). This app lets them upload, mark the court, wait for
processing, and then watch the video with rallies shown as YouTube-style **chapters**
on the scrubber, a rally list, sort/filter by length, and "skip breaks" playback.

Beta scope: rally review only. No shot types, no player tracking, no clip export yet.

## Origin of this repo

Copied from the `frontend/` folder of
[full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template)
(commit `aabb901`, Nov 2026), its MIT copyright notice is kept in `LICENSE` (next to ours). The backend uses

## Running it

Backend first (in `../badminton-backend`): `docker compose up -d`, then
`uv run fastapi dev` in `backend/` (API on :8000), and `uv run python worker/run_worker.py`
for processing. Then here:

```bash
bun install
curl http://localhost:8000/api/v1/openapi.json -o openapi.json   # backend must be running
bun run generate-client                                          # writes src/client/
bun run dev                                                      # http://localhost:5173
```

**Regenerate the client every time the backend's API changes** (the template's
`scripts/generate-client.sh` assumes a monorepo; in our two-repo setup use the two
commands above). Commit `openapi.json` and `src/client/` together.

**Unit tests** (`bun run test:unit`, also in CI): `bun test` over `src/**/*.test.ts`
(excluded from the build's type-check).

**Editor v2 (branch feat/editor-v2).** Built against the backend's edit list v5 (see
"The reel" below; designs docs/design/EditV2*.dc.html; decided: no "match order", no
Lead pill, new clips get a fixed 1 s padding on each side). The shared reel-segments
fixtures are gone (the backend keeps them as v4→v5 migration tests). Don't merge this
branch (or the backend's) into main alone: merge both together.

`.env`: `VITE_API_URL=http://localhost:8000`. It must stay an absolute URL: the
Capacitor app is not served from the API's origin. The backend's CORS settings
must allow `http://localhost:5173`.

**iOS app (Capacitor 8, see `IOS.md`):** `bun run ios:dev` (live reload: Vite on the
Mac's LAN IP, `CAP_SERVER_URL` → `server.url`; Ctrl+C restores the bundled files),
`bun run ios:build` (bundled, backend URL from `.env.ios`), `bun run ios:open`, then ▶
in Xcode. `scripts/ios.sh` runs the Capacitor CLI with `bun --bun x cap` (it needs
Node 22+). App origins the backend must allow (its `EXTRA_CORS_ORIGINS`):
`capacitor://localhost` and `http://<LAN IP>:5173`; it must listen on `0.0.0.0`.
Native differences live in `src/lib/native.ts` (`isNativeApp`; status bar style,
splash, full-screen orientation, native share), all no-ops in a browser. Plain HTTP to
the Mac is allowed in Debug builds only (a build phase adds `NSAllowsLocalNetworking`).
Icons / splash: `bun run icons`. Top safe area: `body` is padded by
`env(safe-area-inset-top)` with a background strip over it; full-height screens use
`h-page` / `min-h-page` (index.css), not `h-dvh` / `min-h-svh`.

`VITE_FEEDBACK_EMAIL`: Profile's "Send feedback" mailto address (hidden when empty).

Tests: `bun run test` (Chromium), `bun run test:webkit` (Linux WebKit in Docker, desktop
Safari + an `iphone` project that runs only `tests/player*.spec.ts`, with the element
Fullscreen API removed like iPhone Safari; the
macOS WebKit build hangs on macOS 26.0). CI (`.github/workflows/test-frontend.yml`)
runs Biome, the build, and both browsers against the backend's `main` and the
production build. In tests, wait for the app's own navigations (`waitForURL`) instead
of calling `goto` right after a click that navigates: WebKit cancels one of the two.
Editor v2's gestures (`tests/video-screen-edit.spec.ts`, 390 px, `hasTouch`, both
themes) are synthetic `pointerType: "touch"` pointer events dispatched on the elements
(Playwright has no touch drags, none at all in WebKit); one pinch also goes through
Chromium's real touch input (CDP). Never `click()` / `tap()` something inside the
timeline: Playwright scrolls it into view first (WebKit even when visible), and
scrolling the timeline moves the playhead. Tap / click at its coordinates instead.

Auth: the template stores the JWT in `localStorage` (`access_token`) and sends it via
the client's `auth` option in `src/main.tsx`; a 401/403 logs the user out. This also
works inside Capacitor.

## Backend API used by this app (prefix `/api/v1`)

All times are **seconds** (float). Court corners are **fractions** of the video's
width/height, order **far-left, far-right, near-right, near-left**.

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /videos/?skip&limit&all`                                                                                                                                                                                | your videos, newest first, `{data, count}`. Superusers: `all=true` = everyone's (403 for others, and the app logs out on 403, so only send it for a confirmed superuser)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

Refusals with a readable `detail`: 413 over 2 GB, 422 over 60 min, 415 not a video type, 400 unreadable. The app checks size (and length, when the browser can read it) first: `components/Videos/uploadLimits.ts` repeats the two limits, the backend still enforces them                                                                                                                                                                                                                                                                                                                                                                                              |

Status `queued`→`processing`→`done`/`failed` (`failure_reason`), `progress`, `duration`, `size_bytes`, `filename`, `created_at` (the edit it shows), `expires_at` (+7 days). Download: `{url, filename, expires_at}` signed link (relative: prefix `VITE_API_URL`), the file is an attachment with Range (plays in `<video>`) |

Off-screen corners (decided in the backend — the app only displays the result):

- up to 10% outside the frame (−0.1 to 1.1): accepted, `court_out_of_frame: false`
- up to 30% outside (−0.3 to 1.3): accepted, `court_out_of_frame: true` → show
  "Part of your court is out of frame, results may be less accurate", let the user
  continue or re-mark
- further: 422 (mis-tap)
  Never re-implement these limits in the frontend; read `court_out_of_frame`.

## Screens and routes (target)

Protected pages go under `src/routes/_layout/` (requires login, has the sidebar).

1. **Videos** (`/`, replaces the template's dashboard): list with filename, date,
   status badge, progress, duration; button to upload; click → the right next screen
   for the video's status.
2. **Upload** (`/upload` or a dialog): pick a video, upload with a **progress bar**
   (axios `onUploadProgress`), then go to Mark court. Short recording tips: tripod
   behind the baseline, as high as possible, landscape, whole court in frame.
3. **Mark court** (`/videos/$id/court`): show the frame with a **gray margin around
   it (30% of width/height on each side)** so off-screen corners can be tapped. User
   taps 4 corners in order (show which one is next), draw the polygon, undo/reset.
   Convert tap positions to fractions of the _frame_ (margin taps give values below 0
   or above 1). Save → show 422 messages inline; if `court_out_of_frame`, show the
   warning. Then "Analyze" → `POST /process`.
   Must work with touch as well as a mouse (pointer events, large targets).
4. **Processing** (`/videos/$id` while queued/processing): poll `GET /videos/{id}`
   every ~3 s with `refetchInterval` only while not done/failed; show status and a
   progress bar. On `failed`, show `error` and a retry button (re-mark court or
   process again). Processing takes roughly half the video's length.
5. **Video screen** (`/videos/$id` when done; `?mode=edit` for Edit) — ONE screen per
   video, two modes (`components/Reels/VideoScreen.tsx`). There is no separate player
   page any more; `/videos/$id/reels/$reelId` only redirects here (old links).
   - Shared: header (back to Home, title, "73 rallies · 18:20 play", "Saved" once a
     reel exists, **Export** (sheet, below), ⋮ Re-mark court / Delete video), the
     video (the rally badge and skip pill in Highlights only), the Highlights | Edit
     tabs.
   - **Export** (`ExportSheet.tsx`, `useReelExports.ts`, `exports.ts`): bottom sheet
     on phones. What the export will be (always the Rallies-only result, said in the
     sheet), quality (1080p only for a ≥1080p recording; `can1080p` repeats the
     backend's check), Export (flushes the autosave first: the server exports the
     saved reel). "Your exports": progress, preview + Share (Web Share API with the
     file, read ahead; else Download) + Download; in the iOS app one "Save or
     share" (native download + `@capacitor/share`, `shareFileNatively`),
     failed → reason + Try again (`POST /exports/{id}/retry`, same snapshot), delete.
     The list `["videos", id, "exports"]` is polled every 2 s only while one is
     queued/processing, by the screen (not the sheet): the header badge and the
     done/failed toasts work with the sheet closed.
   - **Highlights = the player:** the match's **chapter scrubber**, the stats strip
     (this rally, actual play, breaks cut), previous / play / next (+ Undo, full
     screen), keyboard (space, ←/→, ⌘Z / ⇧⌘Z), **"Skip breaks"**, rallies padded ~1 s
     when jumping/playing (detector boundaries can be 1–2 s off). The rally list:
     check circles (pick for the reel), filters All / Picked / Longest, ⋮ rally fixes,
     "+ Missed rally", the `court_out_of_frame` warning.
   - **Edit = the reel (Editor v2):** header "N clips · length", the timeline (edge
     handles, pinch zoom, hold and drag a clip to move it, "+" Add footage) and the
     tools (Cut, Delete, Slow-mo, Text, Format). Clips show no rally names and the
     video no rally badge: a clip is footage; with nothing picked an empty state with
     quick starts (Longest 5, All rallies, Pick from the list → Highlights + hint).

Keep from the template: login, signup, recover/reset password, user settings, admin
(user management), theme toggle, sidebar. Remove: everything **Items** (see M4.0).

**Player building blocks (used by the video screen; compose them in any new screen
with a video):**
`useVideoPlayer` (signed URL with resume/retry, playback state, skip-breaks, full
screen), `VideoStage` (the one `<video>`, inline slot + full-screen layer, overlay
slots), `controls.tsx` (ControlButton, ControlRow, SkipBreaksPill, RallyBadge),
`usePlayerKeys`. A new screen with a video composes these; it doesn't copy them.

**The reel** (one per video, `GET/PUT /videos/{id}/reel`): **created lazily**. Nothing
is picked by default; until the first change (a pick, a cut, a setting) the video has
no reel and the screen works on an empty edit list (watching, filtering, switching
modes never create one). The edit list lives in one reducer with undo/redo
(`components/Reels/reelEdit.ts`; every change is an action there) and is autosaved
(`useReelAutosave`: the empty list counts as saved; 800 ms debounce, one save at a
time, the first PUT sends `updated_at: null` to create; 409 → reload + toast;
`flush` before an export or re-analysis). Query key `["videos", id, "reel"]`
(null = none yet), never refetched in the background (the screen owns the edit list
once loaded); the screen is keyed by video, so creating the reel doesn't remount it.

- **Edit list v5 (`reelEdit.ts`):** a flat list of clips (`Clip` = the API's
  Segment), played in list order. All operations are pure functions on the 0.1 s grid
  (`fitBounds`: inside the video, ≥ 0.3 s): pick (rally ± `CLIP_PADDING`, inserted
  before the first clip that starts after it = match order relative to what's there),
  unpick (all its clips), cut (both parts ≥ 0.3 s), delete, slow-mo, `setClipBounds`
  (edges anywhere in the video), `moveClip`, `insertClip`, captions. New ids from
  `newClipIds` (pure, so the screen knows them before dispatching). One undo step per
  action: an edge drag and a move dispatch once, on release.
- **Timeline math (`timeline.ts`):** reel spans (slow-mo counts double), layout at any
  zoom (px per second, 2 px gaps, min 4 px), x ↔ reel time, `dragEdge` (snap to the
  clip's own rally's detected start / end within 10 px, else 0.1 s). Source time can't
  locate the playhead (clips can be out of order or show a moment twice), so the
  screen keeps a **cursor**: the playing clip, which is also the selected one; reel
  time = its reel start + how far into it the video is.
- **Playback** (`useVideoPlayer`'s `PlaybackRule`: `next(t)` → keep / seek / end,
  `rate`, `restart`; `spansRule` for skip-breaks): Edit plays the cursor's clip, then
  the next in the list (seeking back in time if needed), slow-mo at 0.5, stops after
  the last. A jump of the video from outside the reel (> 0.5 s between frames)
  re-finds the clip that shows that moment. A clip running to the video's end moves on
  0.08 s early (after `ended`, WebKit's play() restarts from 0).
- **Timeline UI (`EditPanel.tsx`, `ReorderStrip.tsx`, `AddFootageSheet.tsx`):**
  gestures are pointer events; one finger scrolls natively (`touch-pan-x`), and a
  non-passive `touchmove` listener on the panel cancels the browser's scrolling / page
  zoom while one of ours runs (edge drag, lifted clip, two fingers). Edge handles are
  `touch-none`; a handle press that doesn't move passes through as a tap on the clip
  under it. Moving a clip has no mode: a long press (250 ms, cancelled by moving more
  than 8 px first, so a swipe scrolls) hands its pointer to `ReorderStrip`, shown only
  until that press ends; it follows the press on `window` (the timeline stays mounted,
  invisible, so the touch keeps its target), moves the held clip relative to where the
  press was, drops on release and selects it. Alt + ← / → on a focused clip moves it.
  A scroll caused by focus (a dialog returning focus to "+") snaps back instead of
  seeking. Add footage excludes "+" from Radix's outside taps, restores focus with
  `preventScroll`, and sits above its overlay (`z-[51]`: on a quick reopen Radix can
  append the overlay after the content).
- **Rally fixes** (`rallyFixes.ts`, Highlights' ⋮ menu): server changes to the match's
  rallies (chapters, list); they never change the reel. The editor calls the endpoint,
  writes the returned list into `["videos", id, "rallies"]`, relabels clips whose rally
  is gone (`relabel`: the rally they show most of, or null) and pushes one history
  entry carrying the fix. Undo calls the reverse endpoint(s) (edit ↔ edit, add ↔
  delete, split ↔ merge, merge ↔ split + edit), redo the forward one; those make new
  rally ids, so the labels in the history entries on that side are remapped
  (`undo-fix` / `redo-fix`).
- Thumbnails (`thumbnails.tsx`): sprite-sheet tiles as CSS backgrounds; the timeline
  draws only tiles near the view, rally rows load theirs when scrolled into view.
  Without a strip (older videos) everything falls back to the drawn court.

E2E tests use real data: `seedAnalysis()` (tests/utils/videos.ts) calls the backend's
development-only `POST /private/videos/{id}/analysis` to finish a video with given
rallies (and optionally the thumbnail strip), the way the worker does.
Exports likewise: `setExportState()` (`POST /private/exports/{id}/state`: processing
at a progress, or failed with a reason) and `renderExport()` (`…/render`: a real MP4
with the worker's ffmpeg renderer, inside the request), so no worker is needed.

**Never use native video full screen for previews (decided).** No
`video.requestFullscreen()`, no `webkitEnterFullscreen()`, no `controls` on the
player's `<video>` (it has `playsinline` + `webkit-playsinline`). On iPhone native full
screen hands playback to Apple's player, which hides our overlays (rally badge, skip
pill, chapter bar, caption overlays) and shows the raw file's timeline.
The player has its own full screen (`components/Player/useFullscreenPlayer.ts`): a
fixed layer with our controls, plus the Fullscreen API _on that layer_ where it works
(desktop, iPad, Android). The one `<video>` is moved between the inline and
full-screen slots, never remounted (no reload, no new signed URL). Exported clips
(later) are real video files: native full screen is fine for those.

**Phones are portrait-only (decided).** Only a full-screen video may turn sideways. The
web can't lock rotation outside full screen, so a phone held sideways sees
`RotateToPortrait` (the `phone-landscape` variant in index.css: touch, landscape,
under 480 px tall); the player's full screen asks for landscape with
`screen.orientation.lock` (Android only; iPhone Safari can't, so the phone is turned
by hand). In the iOS app: Info.plist allows landscape (so the plugin can turn it),
`MainViewController` (`ios/App/App/SceneDelegate.swift`) starts iPhones in portrait,
the full screen locks landscape with `@capacitor/screen-orientation` and `unlock()`
returns to portrait (`lib/native.ts`). Android: not set up yet.

Mobile later (not now, but don't block it): Android, photo-library picker, push
notifications, downscaling the video on the phone before upload (native encoder
plugin) and playing the local original. Design screens to work at phone width now.

## Conventions

- **All UI work must follow `DESIGN.md`.** Read it before touching any screen or
  component: colors, fonts and radii come only from its theme tokens (Tailwind classes
  like `bg-background`, `bg-highlight`, never hard-coded values); a missing color gets a
  token in `DESIGN.md` and `src/index.css` first. Check changes on `/styleguide` in both
  themes and at phone width (390 px).
- All API calls go through the generated client + TanStack Query. Query keys:
  lists `["videos", { all }]`, `["videos", id]`, `["videos", id, "rallies"]`. Refresh
  every list with `invalidateVideoLists()` (it matches `["videos", {}]`: partial object
  match, never a video id) and remove a single video with its prefix; invalidate after
  mutations (save court, process, upload, delete).
- Times in seconds and corners in fractions everywhere; convert to pixels only for drawing.
- Business rules (court limits, status transitions) live in the backend. The frontend
  shows what the API returns.
- Use existing shadcn/ui components before writing new ones; add new ones with the
  shadcn CLI so they match. **After every `shadcn add`**, fix its imports: it writes
  `import { cn } from "cn"` and `import { X as XPrimitive } from "radix-ui"` and installs
  the `cn` and `radix-ui` packages. Use `@/lib/utils` and the separate
  `@radix-ui/react-*` package (`import * as XPrimitive from "@radix-ui/react-x"`) like
