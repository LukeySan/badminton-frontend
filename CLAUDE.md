# Badminton Rally Analyzer — frontend repo (beta prototype)

Read this first. It describes what this app does, how it talks to the backend, the
decisions already made, and the milestones in order.

- Backend repo: `../badminton-backend` (GitHub: LukeySan/badminton-be). Its README
  section **"Using it from the frontend"** and its `CLAUDE.md` are the source of truth
  for the API's behavior.
- Research history and numbers: `../CLAUDE.md` and `../badminton-test/`.

## What the app does

Players record a match on a phone on a tripod and upload it. The backend finds every
**rally** (start/end time). This app lets them upload, mark the court, wait for
processing, and then watch the video with rallies shown as YouTube-style **chapters**
on the scrubber, a rally list, sort/filter by length, and "skip breaks" playback.

Beta scope: rally review only. No shot types, no player tracking, no clip export yet.

## Running it

Backend first (in `../badminton-backend`): `docker compose up -d`, then
`uv run fastapi dev` in `backend/` (API on :8000), and `uv run python worker/run_worker.py`
for processing. Then here:

```bash
bun install
curl http://localhost:8000/api/v1/openapi.json -o openapi.json   # backend must be running
bun run generate-client                                          # writes src/client/
bun run dev                                                      # http://localhost:5173
```

**Regenerate the client every time the backend's API changes** (the template's
`scripts/generate-client.sh` assumes a monorepo; in our two-repo setup use the two
commands above). Commit `openapi.json` and `src/client/` together.

`.env`: `VITE_API_URL=http://localhost:8000`. It must stay an absolute URL: the
Capacitor app will not be served from the API's origin. The backend's CORS settings
must allow `http://localhost:5173`.

Auth: the template stores the JWT in `localStorage` (`access_token`) and sends it via
the client's `auth` option in `src/main.tsx`; a 401/403 logs the user out. This also
works inside Capacitor.

## Backend API used by this app (prefix `/api/v1`)

All times are **seconds** (float). Court corners are **fractions** of the video's
width/height, order **far-left, far-right, near-right, near-left**.

| Endpoint                                        | Use                                                                                                                                                                                                             |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /videos/?skip&limit`                       | video list                                                                                                                                                                                                      |
| `POST /videos/` multipart field `file`          | upload → `VideoPublic` (status `uploaded`); 415 for unsupported file types                                                                                                                                      |
| `GET /videos/{id}`                              | `VideoPublic`: `status` (`uploaded`→`queued`→`processing`→`done`/`failed`), `progress` (0–1), `error`, `duration`, `fps`, `width`, `height`, `court_corners`, `court_out_of_frame`, timestamps                  |
| `GET /videos/{id}/frame?t=1.0`                  | JPEG for court tapping. Needs the login header, so fetch it with the client (as a blob) and show it via `URL.createObjectURL` — not as a plain `<img src>`                                                      |
| `PUT /videos/{id}/court` `{corners: [[x,y]×4]}` | save corners. 422 with a readable message for wrong tap order or a corner too far outside                                                                                                                       |
| `POST /videos/{id}/process`                     | queue (also reprocess)                                                                                                                                                                                          |
| `GET /videos/{id}/rallies`                      | `{data: [{id, start, end, duration}], count}`                                                                                                                                                                   |
| `GET /videos/{id}/file-url`                     | `{url, expires_at}`: a signed, expiring URL for this one video. Use `<video src={VITE_API_URL + url}>`. Refetch a new one when it expires (the video tag can't send the login header, which is why this exists) |

Off-screen corners (decided in the backend — the app only displays the result):

- up to 10% outside the frame (−0.1 to 1.1): accepted, `court_out_of_frame: false`
- up to 30% outside (−0.3 to 1.3): accepted, `court_out_of_frame: true` → show
  "Part of your court is out of frame, results may be less accurate", let the user
  continue or re-mark
- further: 422 (mis-tap)
  Never re-implement these limits in the frontend; read `court_out_of_frame`.

## Screens and routes (target)

Protected pages go under `src/routes/_layout/` (requires login, has the sidebar).

1. **Videos** (`/`, replaces the template's dashboard): list with filename, date,
   status badge, progress, duration; button to upload; click → the right next screen
   for the video's status.
2. **Upload** (`/upload` or a dialog): pick a video, upload with a **progress bar**
   (axios `onUploadProgress`), then go to Mark court. Short recording tips: tripod
   behind the baseline, as high as possible, landscape, whole court in frame.
3. **Mark court** (`/videos/$id/court`): show the frame with a **gray margin around
   it (30% of width/height on each side)** so off-screen corners can be tapped. User
   taps 4 corners in order (show which one is next), draw the polygon, undo/reset.
   Convert tap positions to fractions of the _frame_ (margin taps give values below 0
   or above 1). Save → show 422 messages inline; if `court_out_of_frame`, show the
   warning. Then "Analyze" → `POST /process`.
   Must work with touch as well as a mouse (pointer events, large targets).
4. **Processing** (`/videos/$id` while queued/processing): poll `GET /videos/{id}`
   every ~3 s with `refetchInterval` only while not done/failed; show status and a
   progress bar. On `failed`, show `error` and a retry button (re-mark court or
   process again). Processing takes roughly half the video's length.
5. **Player** (`/videos/$id` when done) — the demo screen:
   - HTML5 `<video>` with a **custom scrubber**: rallies drawn as chapter segments
     (position = time / duration), current-time marker, click/drag to seek
   - **Rally list**: number, start time, length; sort by time or length; minimum-length
     filter; click to jump; highlight the current rally while playing
   - **"Skip breaks"** mode: when playback leaves a rally, jump to the next one
   - **Pad each rally ~1 s** before and after when jumping/playing (detector
     boundaries can be 1–2 s off)
   - keyboard: space play/pause, ←/→ previous/next rally
   - show the `court_out_of_frame` warning here too if set

Keep from the template: login, signup, recover/reset password, user settings, admin
(user management), theme toggle, sidebar. Remove: everything **Items** (see M4.0).

Mobile later (not now, but don't block it): Capacitor build, photo-library picker,
push notifications, downscaling the video on the phone before upload (native encoder
plugin) and playing the local original. Design screens to work at phone width now.

## Conventions

- All API calls go through the generated client + TanStack Query. Query keys like
  `["videos"]`, `["videos", id]`, `["videos", id, "rallies"]`; invalidate them after
  mutations (save court, process, upload).
- Times in seconds and corners in fractions everywhere; convert to pixels only for drawing.
- Business rules (court limits, status transitions) live in the backend. The frontend
  shows what the API returns.
- Use existing shadcn/ui components before writing new ones; add new ones with the
  shadcn CLI so they match.
- Run `bun run lint` and `bun run build` before committing.
